# Model catalog override scope for goal recovery guidance

**Pinned source:** `benchmark-run/shallow`, tag `rust-v0.162.1`, commit `092d3acd6bec3e3a14bdc7e7a2810ab628ab759d`. Exact excerpts and SHA-256 provenance are in `evidence/model-catalog-source/provenance.json`.

## What the catalog can override

The TOML key is `model_catalog_json` (absolute path in `config.toml`). The config schema explicitly marks it “applied on startup only”; per-thread `config` overrides do not reapply it. Core config reads the JSON into a full `ModelsResponse`, requires at least one model, and documents the resulting catalog as replacing the bundled catalog for the current process (`config-key-startup-only.rs`, `catalog-loaded-into-config.rs`, `catalog-read-on-config-load.rs`). The JSON is per model: `models[].model_messages` (`model-info-and-messages-schema.rs`). So the change scope is a model catalog used by that process and the selected model's metadata/tool plan, not an individual request. For source-confirmed behavior, changing this file requires a new process/config load; this tag provides no per-thread hot-reload path for `model_catalog_json`.

Within that schema, `model_messages.tools.send_user_message_async.description` can replace the built-in description used for the asynchronous user-input/attention tool. The resolver falls back to the bundled description when the catalog value is missing or null; an empty string suppresses its static text while preserving tool-owned runtime guidance (`tool-message-schema.rs`, `async-question-override-resolution.rs`). A catalog can therefore clarify when that async tool is useful, such as notifying the user about a hard blocker while work is underway. The tool remains asynchronous: a description change cannot make it wait for a reply or pause a goal loop.

The catalog's built-in `ToolMessages` schema has a specific key list. It includes `send_user_message_async`, `multi_agent`, `code_mode`, and `mcp_resources`, but no `create_goal` or `update_goal` entries (`tool-message-schema.rs`). In this pinned source those goal tools take their static names, descriptions, and status restrictions directly from the goal extension's `spec.rs`; the model tool plan does not consult `model_messages` for them (`goal-tool-built-in-descriptions.rs`). Therefore a model-catalog tool-description override cannot change the goal-creation rule, the three-turn blocked audit, the explicit-user-request requirement for `paused`, the continuation template, or TUI notification/loop behavior.

The separate `model_messages.instructions_template` field is rendered as the selected model's base instructions, and session initialization gives an explicit `config.base_instructions` override and saved conversation base instructions higher priority (`model-instruction-template-resolution.rs`, `session-base-instruction-priority.rs`). That is broader and more fragile than a goal tool description override: it affects base instructions for that model, not just goal recovery; it does not change runtime state-machine rules, and saved base instructions can supersede it.

## Scoped expertise options

For a failure-specific fix, a narrow `AGENTS.md` pointer in the affected repository or directory can route agents to a corrective skill/checklist when the goal loop misfires, async questions vanish, or a hard prerequisite prevents meaningful progress. Keep the instruction diagnostic and scoped: recognize the actual failure first, distinguish optional clarification from a hard blocker, preserve the unresolved question, and use available explicit user controls where required. Such a pointer influences future agent behavior only within its loading scope; it does not alter Codex goal runtime or make a user answer arrive.

An optional goal-recovery skill can hold the longer diagnosis and recovery procedure without adding that material to every turn. It is appropriate when the expertise is invoked after goal-related failures or when such a failure is detected. As an optional skill, it depends on discovery/selection and can be missed; it is not a guaranteed intervention for all requests.

A model catalog override is a third, narrower model-facing lever. The safe fit is `model_messages.tools.send_user_message_async.description` if the goal is to improve the agent's understanding of when to notify the user during ongoing work. It does not directly repair `create_goal`/`update_goal` descriptions or the actual loop. Avoid using `instructions_template` as a substitute for a scoped recovery rule unless a broad model-wide instruction change is intended and the base-instruction precedence has been checked.

## Limits and source boundary

This review reports schema and code behavior from the pinned tag only. It did not inspect the user's live `model_catalog_json`, installed Codex build, agent instructions, skill loading, or perform an inference/runtime test. It does not claim a proposed catalog, AGENTS, or skill change would have fixed the reported session. In particular, none of these model-facing levers changes the active-goal continuation and end-notification suppression paths documented in `goal-source-review.md`.
