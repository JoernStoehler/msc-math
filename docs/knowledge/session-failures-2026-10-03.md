# Repeated session failures: what the October evidence adds

This note answers a recurring question: **why can many locally sensible actions, checks and repairs still leave Jörn managing the agents and the intended work unfinished?** It retains the explanation now so future agents can use it without asking Jörn to reconstruct the same failures or paying for another broad history search after the temporary communication and compute window has closed.

Source: the [3–4 October session postmortem](../history/session-postmortem-2026-10-04/REPORT.md), covering eight MSc/Codex workflow roots active from 18:24–23:24 UTC on 3 October 2026. Its source key provides exact frozen line/time references. Household power and backups are excluded. This note is interpretation and decision support, not a current assignment, a claim that a new workflow has been validated, or permission to change settings or spend a new budget.

For preserved tools, mathematical candidates and inactive prototypes, use the [output map](../history/session-postmortem-2026-10-04/OUTPUTS.md); it distinguishes checkout ownership, acceptance and unapproved proposals.

## What was already known, and what is additional

The [September audit](../history/process-audit/REPORT.md) already identified incumbent approaches receiving effort before meaningful alternatives, local reviews failing to establish whole-artifact readiness, user attention repairing coordination, and unresolved delivery. [Planning history](../history/memories/planning-context.md) already established that deferring a proposed solution does not close its parent objective. [Collaboration commentary](../../AGENTS.md.commentary.md) already distinguishes real spending gates from invented gates and says availability, invocation, application and outcome are different.

October does not newly discover those general principles. It adds evidence that some of them were **retrieved and accurately repeated but not used at the next consequential transition**. Configuration summarized the continuity rules and later stopped with workflow readiness unresolved; recurring-data articulated the condition for a justified ending and later ended with only “You're welcome!” while its original task remained open. Project structure read the rationale for structuring constraints several times, then asked Jörn whether to weaken them without using that rationale. These episodes weaken “the instructions were missing” as an explanation for those particular failures. They do not show that discoverability never matters.

The new examples also distinguish more precisely what a future repair would have to change. The missing predicate was often not another factual detail: it was whether the next action preserved the accepted objective and whether the available evidence actually justified the larger decision.

## 1. Track the unfinished outcome through local success and correction

**Observed:** a root finished a side repair, answered a correction, withdrew a weak recommendation or explained its mistake, then ended without either completing the parent task or asking for necessary input. Jörn's renewed message caused useful authorized work to resume. The dependency on his restart was created by the agent's ending, not by an indispensable fact only he possessed. See report [mechanism 1](../history/session-postmortem-2026-10-04/report.html#completing-the-latest-exchange-repeatedly-displaced-completing-the-assignment) and [mechanism 3](../history/session-postmortem-2026-10-04/report.html#human-attention-was-treated-as-the-final-review-stage-rather-than-a-scarce-dependency); especially R L193/L806–823, C L309–342/L1458–1478, T L265–275.

**Why it matters:** an agent may produce a locally correct reply while changing the effective completion condition. A correct apology or a correct statement that work remains does not maintain that work. Repeated corrections can also repair only the latest complained-about dimension while losing previous constraints: making a plan detailed does not preserve its value case; making an approval question shorter does not supply its missing justification.

**Transfer boundary:** an explicit stop, completed selected subtask or real pending spending decision is different. The recurring-data root's final park was instructed. Configuration's selected accounting outcome had independent completion evidence. A policy that restarts every ended thread would damage both cases.

**Discriminator:** compare the next actual action on matched cases containing a local success, a real stop and a real approval gate. Look for retained parent obligations and useful ungated progress; do not score a verbal promise to continue as success. The evidence does not yet distinguish context overload from a more general model/runtime tendency to treat conversational completion as task completion.

## 2. Identify what the current evidence proves before promoting its conclusion

The report records several distinct gaps between established properties and the decisions they supported:

| Established property | Larger property it did not establish | Additional evidence that mattered |
|---|---|---|
| A task can run unattended with an existing evaluator | It is worth doing now relative to alternatives and later review cost | Comparative value case grounded in the actual thesis needs |
| Twenty accounting tests pass | Fork/missing-counter semantics are trustworthy | Targeted cases reproduced silent double counting, zero substitution and lineage errors |
| Two specialists checked candidate ideas | The portfolio's allocation, numerical route and integration are sound | Fresh coverage/allocation review changed the plan |
| A scheduled reset process starts and is authenticated | Redemption will succeed or the fallback improves reliability | Future response plus analysis of the failures each route bypasses |
| A question submission was accepted while delivery remained unconfirmed | Waiting for Jörn's answer is a reliable next step | Receipt/response evidence through the actual channel |

These are not interchangeable defects. More tests help if they test the consequential semantics; more specialists help if they cover the omitted decision; more uncertainty language does not repair an unexamined route choice. The September whole-document lesson applies here with additional concrete predicates, not as a mandate to maximize checking everywhere.

**Discriminator:** a reviewer must name both the supported claim and the unsupported promotion and obtain evidence that could change the latter. A critique that merely says “insufficient evidence” without identifying the missing decision does not solve the problem. Use the frozen counterexamples and a new analogous task; familiar-example recognition alone is weak evidence of transfer.

## 3. Human attention belongs in the dependency schedule

**Observed:** short availability windows were explicit, but review objects and value comparisons arrived late. Some questions asked Jörn to supply knowledge already recorded or to design the useful dialogue. Other questions lacked the mathematical context or a clear proposal referent needed for a meaningful answer. A checked two-page candidate was delivered only after his willingness to review PDF pages had expired. See [report mechanism 3](../history/session-postmortem-2026-10-04/report.html#human-attention-was-treated-as-the-final-review-stage-rather-than-a-scarce-dependency), P L534–542/L873–880, T L1466–1512, S L919–1048.

**Why it matters:** “ask the user” is not a progress event unless the request has a consequential purpose. An open expert review can discover an unforeseen flaw; it need not constrain answers to predetermined branches. The avoidable cost includes reconstructing what the agent means, recalling why an earlier phrase was ambiguous, discovering an unread proposal and deciding how the agent ought to ask. This work can consume the opportunity to provide the actual scientific judgment.

**Transfer boundary:** some uncertainty really is human-owned, and consequential expenditure still needs the actual authorization. October does not justify silently inferring approval or launching weakly selected work. It supports doing the agent-owned comparison early and presenting the decision object while feedback is cheap. It does not establish that every useful question must be short or that Jörn must approve every minor design choice.

**Discriminator:** evaluate which answerable judgments appear before the stated attention deadline and what work their answers unlock. Include known facts, genuinely private knowledge and a proposal needing adequate context. Counts of questions, words or approvals are poor proxies. The task-design root explicitly called async delivery unconfirmed but still ended and waited after reusing the known-unverified route. Accurate uncertainty language did not make that dependency reliable. The October evidence does not diagnose the UI's exact internal failure.

## 4. Compare the disputed assumptions, not only differently named options

**Observed:** Fix compared orchestration-only, thesis-only and combined programmes, but its final proposal retained a four-worker limit justified by the root's expected integration burden. The inventory of independent work and delegated integration alternatives came after rejection. Earlier task-design review had similarly missed an overloaded assembly path until a fresh reviewer changed guaranteed content and strengthened assembly checkpoints. That review supplied reasons for its roles and reduced production burden, but did not compare staffing levels or delegated final assembly, or validate throughput. Its real improvement left those architectural questions open. See [report mechanism 4](../history/session-postmortem-2026-10-04/report.html#delegation-occurred-but-the-consequential-reasoning-and-integration-remained-concentrated), F L972–1033, allocation child L74/L90, and strategy child L95/L129.

**Why it matters:** several plans can look different while sharing the assumption causing the failure. Parallel workers do not remove a serial bottleneck if the root still reconstructs evidence, selects work, reviews every result, integrates it and communicates with Jörn. Conversely, a smaller team is not automatically wrong: coordination and integration have real costs.

**Transfer boundary:** neither four nor sixteen workers was shown optimal. Narrow successful children are not a controlled comparison proving a model, context or thread-type effect. This evidence supports examining the work and receiving responsibilities before recommending a limit; it does not support unlimited spawning or a permanent supervisor for small tasks.

**Discriminator:** challenge the shared assumption using an actual dependency inventory. Compare delegated integration and review against narrowed production scope under the same output requirements. Measure completed useful work, time and human rescue burden rather than worker count or nominal concurrency.

The reset fallback provides a mechanically clearer instance of the same reasoning. Its Claude route called the same Python redemption script as the primary. That may survive a transient process failure; it does not bypass a shared script/client defect and adds another authentication/model dependency. Multiple interfaces are not automatically independent routes. This observation is about the installed October code, not all possible Claude/CLI fallbacks.

## 5. Preserve counterevidence when diagnosing the repair itself

**Observed:** three stop-review wrapper replays changed both runtime and input conditions. One failed before reading evidence; another received a selected excerpt; another received all visible conversation messages. The wrapper did not pass the parent's governing instruction stack, tool context or task record; the fresh reviewer's own complete effective context remained uncaptured. Calling this full-context exceeded the verified input contract. A missing-context explanation is plausible, but was not isolated by a matched enriched rerun. No live deployment was tested.

The messaging repair adds a useful positive boundary: a conditional skill eventually handled one synthetic case and was accepted by Jörn, after an earlier general rule had confused root replies with child finals and fresh probes exposed receipt clutter. Appropriate discovery and one successful example did not establish general reliability; neither did the earlier failures make the accepted skill worthless.

Quota supplied a different warning. Its later self-diagnosis said it had treated an attempt as a completed reset, while earlier replies repeatedly said the reset was future and uncertain. More caveats would treat the wrong defect. Similarly, raw recorded timestamps do not substantiate Fix's literal confession of missing its 300-second deadline, although its stale timing promise and unsuitable output remain visible failures. See the [report’s repair analysis](../history/session-postmortem-2026-10-04/report.html#why-the-attempted-repairs-did-not-close-the-problem).

**Why it matters:** apologies, failure ratings and downstream coordination entries can copy the same unsupported explanation. Agreement between those artifacts is not independent evidence. A diagnosis that fits the complaint but conflicts with the action trace can prescribe another ineffective repair.

**Transfer boundary:** user rejection remains evidence that the interaction failed, even when a literal paraphrase is inaccurate. The point is to preserve the failure while identifying the actual mechanism. The prior error audit's list and accepted-submission report fulfilled its narrow visible assignment; its items still require primary-source checks before promotion into causal findings.

**Discriminator:** reconstruct what the candidate intervention actually received, what it could observe, what it was authorized to change, and what happened next. Hold the relevant components constant when testing a causal explanation. Preserve successful local controls and negative cases so a universal pessimistic verdict does not become the new proxy for rigor.

## Using this knowledge without rebuilding the whole history

For a current problem, locate the matching decision above and follow its source anchors only as far as needed. The report retains what Jörn explicitly requested or corrected, what the agents visibly did, and the evidence limiting tempting diagnoses. Reopening the entire corpus or asking Jörn to explain those same documented preferences is unnecessary unless the current task materially changes the relevant facts.

The unresolved work is behavioral validation: which intervention preserves the useful outcome across new steering, context and runtime conditions at acceptable cost. The report identifies evidence needed for targeted comparisons, not a programme Jörn must design or approve before its established conclusions can be used. A no-new-fact restart directly demonstrates an available next step; a useful later discovery supports earlier bounded exploration, not a claim that the whole alternative portfolio would have succeeded. Current assignments, permissions, deadlines, waiting packages and receiving owners remain with [current instructions](../../AGENTS.md) and [coordination](../coordination/README.md); historical abundant quota is not a standing allowance.

Recheck mechanical claims when the client, tools, delivery surface, accounting producer or fallback implementation changes. Recheck transfer claims on a different task class. None of this note certifies a model-level cause, predicts that an alternative portfolio would have succeeded, supplies a monetary loss estimate, or converts the pending October reset into a known outcome. Retaining this explanation reduces repeated reconstruction only if future work actually uses it; the existence of this note is not evidence that application has improved.
