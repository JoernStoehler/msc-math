## Code Review: Rust Optimizations

### LU fast path (lib.rs:169-178)

**Correctness:** Sound. `full_piv_lu()` is numerically robust. `is_invertible()` guards against rank-deficient systems. SVD fallback preserves handling of degenerate cases (e.g., hypercube 4-facet orbits in 2D symplectic subplane). Residual check (line 181-183) validates every solution regardless of solver path.

**One subtlety verified:** The Q computation (lines 189-198) computes directly from `omega0(n_i, n_j)` with `i > j`, NOT from H matrix entries. The comment correctly explains why: H is symmetric with H_ij = omega0(n_min, n_max), but Q needs the ordered form. This is unchanged from before.

### H matrix elimination (lib.rs:141-148)

**Correctness:** The `omega0` calls and symmetry assignment are identical to the old code — just inlined directly into the KKT matrix instead of going through an intermediate allocation. Verified by diff inspection.

### Lazy permutations (permutations.rs)

**Correctness:** Heap's algorithm is standard and correct. Single buffer reuse is safe (callback receives `&[usize]` valid only during call). `cyclic_permutations()` preserved as thin wrapper for backward compatibility. `ehz_capacity()` (unpruned) still uses the old API; `ehz_capacity_pruned()` uses the new callback API.

**Note:** `ehz_capacity()` still allocates all permutations eagerly (line 79). This is fine — the unpruned version is only used in tests, not in production.

## Findings

### Issues

1. **Minor: benchmark.tex growth rate inconsistency.** The text says "4.76× per facet" (line 61-64 of benchmark.tex) but systolic-ratios.tex says "~4.8× per facet" (line 133). Both come from the same model (b = 4.758...). Not wrong, but Jörn should decide if he wants exact consistency. Suggested fix: use "~4.8×" in both places, or "4.76×" in both.

2. **Minor: `iterations` counting differs between pruned/unpruned.** In `ehz_capacity()` (unpruned), `iterations` counts ALL (S, σ) pairs. In `ehz_capacity_pruned()`, it counts only pairs that PASS the adjacency filter (line 282). The `iterations` field in PolytopeRow documents "Number of (subset, permutation) pairs evaluated" — "evaluated" is ambiguous (does it mean "tested" or "passed filter"?). The pruned version's count is what goes into the dataset, so the data is self-consistent, but the doc comment could be more precise: "pairs where KKT was solved" or similar.

3. **Observation: existing clippy warning.** `from_polytope` has 8 arguments (clippy limit: 7). The `iterations` parameter (new in this branch) pushed it from 7→8, crossing the threshold. This is a reasonable tradeoff — alternatives (builder pattern, config struct) are over-engineering for a data constructor. Jörn's call.

### Strengths

1. **Mathematically verified optimizations.** LU→SVD fallback correctly handles the rank-deficient case, and the residual check catches any solver failure. Property tests (pruned=unpruned) provide strong evidence that no valid orbits are lost.

2. **Complete data pipeline.** End-to-end from Rust → JSONL → Python → JSON → LaTeX, all field names and values consistent.

3. **Well-calibrated confidence assessment** in systolic-ratios.tex. Honestly states limitations (small samples at high F, sampling bias toward generic polytopes).

4. **Pragmatic F≤12 cap.** Documents exactly why F=13-14 are one-off, with timing evidence. Routine regeneration stays fast (~3min).

5. **Profiling methodology documented.** Not just "we made it faster" but callgrind instruction counts, before/after wall-clock, memory profiling with massif. Two discarded optimizations documented with reasons.
