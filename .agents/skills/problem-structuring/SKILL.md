# Problem structuring

Develop enough understanding of what work is worth doing for reliable independent progress, while reducing avoidable interruptions, context switching and confusion. Do not assume that a settled goal already exists. A focused conversation is a means to that outcome. Short messages, few questions, an approved plan and completed subtasks are not substitutes for it.

Efficient interaction is an enabling condition for this work, not a separate polish step. Problem and goal development must remain feasible within shared resources: elapsed time, tokens/context capacity, user attention and frustration tolerance, and the agent's ability to retain a coherent account of the discussion. Avoidable repetition, tangents and poorly prepared questions can consume those resources before the problem becomes workable. Assess total useful progress per interaction, not brevity alone; enough context and substantive investigation can reduce total cost even when an individual exchange is longer.

## Establish the problem and useful next decision

Start from what the user brings: observations, dissatisfaction, questions, possibilities or partial goals. Do not assume that these specify a task, or that the user already knows which outcome would be best. Use existing context and confirmed choices without treating them as a complete answer. Investigate candidate understandings through concrete examples and cheap probes. Develop them with the user when their knowledge, judgment or authority can resolve something the agent cannot. Keep uncertainty and consequential competing framings visible. Develop the goal and the problem together, and revise them when findings change what seems worth doing.

For a heterogeneous topic, identify coupled questions and independently investigable parts. Resolve a concrete consequential uncertainty at a time; do not make an unrelated design decision block all useful work. Rejecting one proposal does not dispose of its parent objective.

Assess approaches by their effects on result quality, reliability, user effort, resource cost, latency and maintenance together. Do not choose a format, transport, metric or convenient implementation first and reshape the problem to fit it. Compare real alternatives at the same level and preserve their conditions. Improving the latest criticized dimension does not establish that the whole recommendation is adequate.

In this project, `docs/project-facts.md` owns attributed scope and `docs/knowledge/README.md` routes relevant evidence. Retrieve only context that can change the decision. Historical plans and backlog items do not establish current authorization.

## Concentrate necessary interaction

Investigate facts and alternatives the agent can recover before asking the user. Identify remaining decisions requiring their knowledge, judgment or authority. Do not ask them to rank speculative remedies or choose a cause of agent failure without an assessable comparison. An uncertainty in agent reasoning is not automatically a question the user can answer.

When related decisions can be considered together, prepare a focused synchronous conversation: intended outcome, concrete object/example, enough context, consequential uncertainty and how the answer changes the work. Ask the actual question plainly; omit narration that hides it. Let answers revise the decomposition or remove later questions. Numbered claims, drafts in the user's terms and small probes are options, not required rituals.

Watch whether exchanges are resolving uncertainty or merely consuming the session. When they loop, recover the specific unresolved issue and accepted corrections, change the question or probe, and keep the shared account concise enough to remain usable. Do not repair only the latest criticism while forgetting the whole problem. If a context or session handoff becomes necessary, carry the current framing, decisions, live disagreements and next useful action rather than making the user reconstruct them.

Some questions only become answerable after findings. Name the finding that will expose them and perform useful authorized work first. Do not demand a complete upfront specification when discovery changes the problem. Collect related new questions when delaying them will not invalidate useful work.

Use current chat for focused exchanges, accessible review artifacts for substantial objects, and annotations when located feedback helps. Distinguish failed delivery from failed understanding. Change the surface or repair the context accordingly, preserving the pending decision. In this project the async question tool is disabled: ask directly in chat. A channel change grants no approval.

## Continue independently and return with evidence

Retain the goal, decisions, important uncertainty and authority with the existing coordination owner when material. A bounded exploratory assignment may be ready before an implementation plan. A handoff carries the open question, scope and result/return contract; it does not turn uncertainty into an assumed requirement.

Proceed where intent, constraints and assessment are sufficient. Use reasonable explicit assumptions for nonessential details; keep required decisions pending. Do not invent approval gates for authorized small work. Preserve actual substantial-spending and other established approval boundaries.

Return when findings invalidate a consequential premise or expose a decision requiring the user. Supply the new evidence, precise question, recommendation where justified and effect of the answer. Reopen settled matters only for a reason.

Corrections, acknowledgments and questions normally steer existing work. Incorporate them and continue. During unfinished work, take the useful authorized next action rather than ending with narration of an action not taken. If progress genuinely requires input, present that request visibly. Finish when the intended deliverable is complete, the user stops, or necessary input is explicitly pending. Do not invent further work to avoid ending.

## Assess the intended result

Check whether the work serves the objective developed with the user, not just whether a procedure ran. Match conclusions to evidence. Distinguish component completion, structural validity and the whole outcome. If guidance was read but the agent still chose poorly, another copy or file arrangement is not an established repair.

When maintaining this skill, read [design notes](references/design-notes.md) for its incidents, decisions and unresolved alternatives. These notes are design memory, not an additional execution-policy owner.
