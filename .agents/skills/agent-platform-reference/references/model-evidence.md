# Model behavior: evidence and open questions

The same technical-reference skill holds product mechanics and model-behavior evidence. The certainty levels differ. Product documents describe interfaces and intended behavior; neither a vendor prompting guide nor an appealing explanation establishes why a model failed or predicts the effectiveness of a new workflow.

## Keep the system layers separate

Record the underlying model/provider/version and effort separately from the client, available tools, context construction, compaction, instruction hierarchy, memory, orchestration and UI. An active-goal notification gate is harness behavior. Inferring a product goal from an ordinary heading is a model/harness interaction whose exact activation trace is needed. Long serial execution could reflect task dependencies, delegation policy, tool availability, quota constraints or agent planning—not necessarily intrinsic inability to do mathematics.

## Evidence classes

- **Documented contract/vendor claim:** source URL or tagged implementation; state its product and version scope. Vendor performance/prompting claims remain vendor claims unless independently checked.
- **User-reported observation:** retain exact task, symptom, known environment and missing trace. Don't turn a hypothetical example into an adopted configuration or measured incident.
- **Executed observation:** preserve input, output/artifact, environment/configuration and trace. A fixture run establishes what that fixture exercised, not a live UI or general model property.
- **Comparative experiment:** state controls, replication, costs and confounds; keep negative outcomes. A disclosed-case repair is not a held-out benchmark.
- **Hypothesis:** give competing mechanisms, what would distinguish them and what remains unknown. Plausibility is not a conclusion.

## Incremental additions after this skill exists

Add findings at their owning scope: source-backed facts to product references; observed defects/caveats to the correction register; raw reports/traces to evidence; conditional expertise to a specialized skill only when it serves a distinct workflow. Do not promote a tentative model-behavior story into a global rule. Preserve its uncertainty and contrary observations through later edits.

A new record should include: ID/date; question/task; surface/model/version/configuration; observed input/action/outcome; evidence location and provenance; interpretation and alternatives; demonstrated boundary; next discriminating test; maintained consumer; review status. Use `evidence/model-behavior-records.json` as a minimal example, not a claim that this package has completed model-behavior research.

## What this package currently establishes

It has primary-source mechanics, tagged source observations, acquired corpus/tooling validation and disclosed-case diagnosis/artifact demonstrations. It does not establish a model-wide failure rate, mathematical capability curve, optimal swarm size, a causal context-contamination mechanism or a reliable unattended research strategy. The user retains withheld acceptance cases. Subsequent traced work can extend this skill with measured findings and create other skills in parallel without replacing the one technical owner.

For time attribution, consult [session-traces.md](session-traces.md). Classify measured spans and unobserved intervals; don't infer compute effort or cognitive quality from token count, message count or gaps between transcript entries.
