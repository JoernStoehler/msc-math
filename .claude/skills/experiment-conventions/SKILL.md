# Experiment Conventions

## Directory Layout

```
experiments/
  Cargo.toml             Builds all experiment Rust binaries (depends on symplectic crate)
  reproduce.sh           Source of truth for full pipeline (zero data → thesis PDF)
  IDEAS.md               Research directions, priorities, deferred ideas
  <name>/                Per-experiment folder
    logbook.md           Prose: motivation, attempts, interpretation, figures, how to run
    math.tex             Formal: proofs, definitions, derivations (needs LaTeX rendering)
    run.rs               Rust binary source
    analyze.py           Python analysis script
    data.jsonl           Dataset (generated by Rust binary)
    *.png                Figures (generated by Python script)
  requirements.txt       Python dependencies
```

The folder name provides the namespace. Files inside use role-based names (`run.rs`, `analyze.py`, `logbook.md`, `math.tex`), not `<name>.rs`, `<name>.py`.

**Legacy:** Existing experiments use `<name>.rs`, `<name>.tex`, and `README.md`. New experiments use the role-based names. Rename old files opportunistically when touching them. When renaming `<name>.rs`, update the `[[bin]]` entry in `Cargo.toml`.

## Two Living Documents

Each experiment has two complementary living documents. Neither is a polished thesis section — both evolve as the experiment progresses.

### logbook.md — the prose document

The logbook is the **entry point** for any agent or human looking at an experiment. Read it first. Write into it during work, not after.

**Contents:**
- **Motivation:** What thesis question does this address? Why does it matter?
- **Status:** Current state (active / paused / complete / abandoned)
- **How to run:** Reproduction commands, file listing, dependencies
- **Attempts and outcomes:** What was tried, what happened, what the data showed
- **Figures and discussion:** Embed or reference figures, discuss what they show
- **Interpretation:** What the results mean. Label speculation as interpretation.
- **Dead ends:** What was tried and abandoned, and *why* — so future agents don't retry it
- **Deferred ideas:** Directions paused with resume conditions ("worth revisiting if we get F>12 data")
- **Open questions and blockers:** What's unclear, what's needed to proceed

**Every entry records *why*, not just *what*.** "Ran sweep" → "Ran sweep because we suspected bimodal distribution at F=8, based on the outliers in the random-sweep data."

**Preserving Jörn's words.** When Jörn provides commentary, questions, or corrections, record them with the `Jörn:` prefix and preserve his exact wording. Don't paraphrase, don't substitute words, don't "clean up" phrasing. Spelling fixes are fine; semantic changes are not. Example:
```
**Q: Is Phase B data complete?**
Jörn: dunno, so probably not regenerated. sys-optimization didn't use proper gradients iirc and didn't look at cuts
```

**When sources conflict** (e.g. during migration from old README to logbook), flag the conflict explicitly and check the data (JSONL/output files) as ground truth. Don't silently pick one version.

### math.tex — the formal document

Proofs, definitions, derivations, formal statements — anything that needs LaTeX math rendering. Also a living document that grows alongside the logbook. Load the `math-tex` skill for full conventions.

### What goes where

| Content | Location |
|---------|----------|
| Why this experiment exists | logbook.md |
| How to run / reproduce | logbook.md |
| File listing | logbook.md |
| What we tried and what happened | logbook.md |
| What the results mean | logbook.md |
| Figures and visual discussion | logbook.md |
| Dead ends and deferred ideas | logbook.md |
| Proofs and formal derivations | math.tex |
| Definitions and theorem statements | math.tex |
| Code documentation | code comments |
| Raw data | .jsonl files |

No README.md. No duplication between files.

### Staleness convention

Logbook entries grow stale as the experiment evolves — old interpretations get superseded, figures get regenerated. This is fine:
- Old entries are kept so context isn't buried in git history
- Old figures/data referenced by stale entries live in git history
- Don't update old entries to match new figures
- Don't delete old entries
- Just add new entries — the current state is at the bottom

## Agent Behavior

### Before starting work

1. Read the logbook. Know why this experiment exists, what's been tried, what's worth pursuing.
2. Check IDEAS.md and TASKS.md. Understand where this experiment fits in the project.
3. If the current direction seems low-value compared to alternatives: say so and propose switching. Don't mechanically complete work that no longer matters.

### During work

4. Write into the logbook as you work. Record decisions, results, interpretations, surprises.
5. If stuck for extended time on something that isn't working: record it as a dead end in the logbook (with reason + resume conditions), move on to something more productive.
6. If you discover something unexpected: record it immediately. Surprises are the most valuable findings and the easiest to lose.

### When pausing or abandoning

7. Write in the logbook: what was tried, why it's being paused, and under what conditions it would be worth resuming. "Deferred" ≠ "dropped."

### Before presenting to Jörn

8. Self-review: dispatch a subagent to re-read the logbook and math.tex and check:
   - Does the logbook explain *why* this experiment exists?
   - Are all factual claims verified against data?
   - Are proofs in math.tex correct (preconditions checked, steps justified)?
   - Is there higher-value work available right now?

## Pipeline

Rust binary → .jsonl → Python script → figures → thesis

- Python never calls Rust directly
- Rust binaries built from `experiments/Cargo.toml` (`cd experiments/ && cargo build --release`)
- To add a new experiment: create `<name>/` folder, add `[[bin]]` entry to `Cargo.toml`, update `reproduce.sh`
- `reproduce.sh` is the single source of truth for the full pipeline (zero data → compiled thesis)

## Data and Figures in Git

**Tracked (committed):**
- `*.jsonl` — datasets generated by Rust binaries
- `*.png` — figures generated by Python scripts
- `*_output.txt` — stdout from binaries whose deliverable is stdout

**Regeneration:**
- Regenerate on the branch that changes the code. Data should match the code that produced it.
- Separate commits for code changes vs data regeneration.

**Merge conflicts (data/figures):** Resolve by regenerating on the merged result.

## Library Boundary

Stable, shared code lives in `crates/` and experiments import it:
- `symplectic::Polytope4D` (or `symplectic::geom::polytope::Polytope4D`)
- `symplectic::ehz_capacity`, `symplectic::billiard_capacity`
- `symplectic::volume`, `symplectic::omega0`
- `symplectic::known_polytopes`

Only stable, proven code goes into `crates/`. New algorithm variants stay self-contained in experiment binaries until promoted.

## Quality Standards

**Rerunnable from zero:** Starting from empty data, running all scripts reproduces all outputs. No manual steps.

**Document assumptions:** If a script assumes a file exists, say so in the header and error message.

**Not production code:** Focus on clarity and correctness over performance. Reproducibility matters, exhaustive testing doesn't.

## Writing Rules

**Write up what's there — nothing more, nothing less.** Facts are facts, correlations are correlations, unknowns are unknowns. Speculation must be labeled as interpretation.

- Every factual claim verified against actual data (JSONL) in the same session
- Unverifiable claims marked with `% [TODO: JÖRN -` or `% [GAP -`
- Agent-generated content is a draft until Jörn reviews
- Statistical claims require reproducible computation
