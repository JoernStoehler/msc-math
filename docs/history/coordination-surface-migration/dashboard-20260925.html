What must this tool enable?

Use this view to challenge the proposed conditions for a useful dashboard. A polished page is insufficient if it cannot support timely, informed feedback.

1. Reconstruct the present situation cheaply

The reader can find the thesis target, material uncertainty, current work, idle ready work and next decision without a long search.

2. Trust and correct the picture

Material claims show scope, evidence and age. Work coverage is explicit, so absence does not masquerade as completion or blockage.

3. Remain current during real work

Changes in goals, evidence, owners, blockers or decisions reach one editor and either appear on the page or visibly mark it stale.

4. Be easy to reach and answer

Jörn has a stable URL and can point to a specific claim when giving feedback.

These are proposed dashboard criteria, not thesis-PASS requirements or an agreed service level. Coverage and end-to-end use remain unproven.

How would this stay trustworthy?

Use this view to distinguish the present manual snapshot from the proposed maintenance process. It is not operating yet.

Today

The thesis dashboard names its manual source baseline. A freshness endpoint checks nine cited source files, not every supporting claim. Project guidance assigns reconciliation to the agent making a material change or the integrating agent. No continuing editor or tested handoff loop exists yet.

Proposed update contract

When a worker changes a claim, selected result, owner, blocker or next decision, they report the changed fact, source path and revision, evidence strength, and next action. One editor checks those deltas against the source and replaces superseded status text. If reconciliation is pending, the affected view says so visibly.

Before calling the update process live

Name a continuing editor and successor, test a real change through the update loop, and extend freshness checks beyond the nine cited files. Those update conditions are untested.
