# Collaboration guidance: situation-first analysis and selected project skills

**Status, 6 October 2026:** Jörn authorized replacement of the relevant project skill set on 5 October. The selected project packages are `problem-structuring`, `external-agent-communication` and stable-named `harness-engineering`; the old `agent-skills` plugin is disabled only for this project. Its unrelated capabilities began as preservation copies; the [full-set pre-sweep](../../docs/history/skill-presweep-20261006/README.md) records subsequent bounded repairs and maintenance companions for all nine packages. The packages are installed. [Validation](skill-replacement-validation-20261005.md) retains initial fresh Codex/Claude discovery evidence; those checks precede the later source revisions. Broad behavioral benefit remains unestablished.

## Goal

Help agents develop a shared understanding with Jörn of what project work is worth doing, then carry it through independent execution and integration with less avoidable user effort and confusion. The goal and problem may need to develop together; a settled, extractable intent is not assumed. Evaluate quality, reliability, user attention, resources, latency and maintenance together. Neither few files nor short conversations is the objective.

Jörn requested: analyze problems; identify content agents need in the relevant situations; then optimize presentation and triggers. He proposed focused synchronous interaction before autonomous work where feasible, with later escalation when that proves insufficient, and a separate capability for exchanges across independent agent contexts. Standard native subagent-tree transport does not need another skill.

## Content required in the actual situations

| Situation | Content needed before acting | Completion at that stage |
| --- | --- | --- |
| Rough or heterogeneous input | Observations, dissatisfaction, questions, possibilities and partial goals; existing context/choices; candidate framings, probes and coupled versus independent questions | Enough shared understanding of the evolving problem and goal for a useful next investigation or user decision; no presumed complete intent or arbitrary whole-topic implementation |
| Unclear approach | Evidence retrieval, real alternatives, downstream effects, consequential uncertainty and cheap probes | A justified next step; no requirement to finish every design decision before independent work |
| Necessary human involvement | Concrete object, sufficient context, question and consequence; what agents can investigate first; grouping related decisions without assuming all can be frontloaded | Decisions or substantive clarification that enable useful autonomy; a clear account of what will need later findings |
| Autonomous work and emerging surprises | Intended outcome, actual authority, assessment and assumptions; evidence that should reopen a decision; continuity across steering and acknowledgments | Useful independent progress, or a specific evidence-backed request; not another narrated plan followed by a stop |
| Independent context exchange | Recipient/action/reply semantics; destination/channel comparison; sufficient brief; scope/resources/return/integration; concrete route instructions | Material and replies available through a workable route, with evidence for the delivery state |
| Return and integration | Assignment matching, consequential result review, evidence retention, ordinary source owner, parent objective and remaining obligations | Useful findings integrated; component success and whole completion remain distinct |

Focused synchronous conversation is a candidate way to concentrate human involvement. Some work depends on discoveries and needs later interaction; guidance should preserve that possibility instead of claiming complete upfront specification. A routine update does not need a research-planning procedure. A clear small task does not need a scoping interview.

This inventory corrects the assumed context: the user's goal may still be developing (I1), the task may be clear but the judgment poorly supported (I3/I4), or the work may already be ready for autonomy (I6/I7). Those situations cannot be treated as one generic missing-intent problem.

The selected problem-structuring trigger covers readiness for autonomous work whether uncertainty is agent-resolvable or requires the user. The earlier joint-only `work-with-user` candidate would have dropped independent decomposition from the upstream capability; review therefore broadened the trigger and retained the canonical problem-structuring name. The agent must determine whether user interaction can supply anything useful before initiating it. General continuation failures still do not justify a full structuring procedure. Selection of the project replacement does not establish reliable selection or application at these encounter boundaries; those remain questions for behavioral evaluation.

**Dependency clarified by Jörn, 5 October:** Useful, efficient interaction enables collaborative problem development; it is not a separate outcome to optimize later. Otherwise time, tokens, attention, frustration tolerance and agent context coherence may be exhausted before the problem becomes tractable. The incident rows distinguish starting contexts, not independent workflows. Guidance for question preparation, conversational focus, accumulation of corrections and preservation of a usable shared account therefore belongs inside problem structuring. This does not make minimum message length or minimum question count the objective, or imply that every uncertainty can be resolved upfront.

## Presentation following the content

The approved replacements use project discovery paths:

- [Problem structuring](../../.agents/skills/problem-structuring/SKILL.md): one abstract readiness trigger for work needing problem, goal or decision development. It preserves agent-resolvable decomposition and investigation; focused user interaction applies where needed, rather than defining the entire trigger. Its sections connect interpretation, investigation, interaction, independent progress and evidence-backed return.
- [External agent communication](../../.agents/skills/external-agent-communication/SKILL.md): one broad trigger for independent-context exchange. Technical usage and common message/reply contracts come first, followed by conditional assignment/decision guidance and integration. The inline technical section gives preferred supported paths by operation/environment and the complete Pro round trip.

Following Jörn's maintainability preference, both descriptions now state the abstract applicability condition before concrete recognition examples. Skill-specific design memory lives in `references/design-notes.md`: [problem-structuring notes](../../.agents/skills/problem-structuring/references/design-notes.md), [communication notes](../../.agents/skills/external-agent-communication/references/design-notes.md) and [harness notes](../../.agents/skills/harness-engineering/references/design-notes.md). These record rationale, incidents, decisions and alternatives for maintenance rather than expanding every runtime load. The selected packages use this single companion path; their earlier `SKILL.commentary.md` companions were folded into the design notes and removed. Historical inactive candidates remain unchanged.

These are content groups frequently needed together, not one skill per sentence. The descriptions round outward to catch rough conversational input before premature implementation and recipient selection before delivery mechanics. Body instructions narrow the procedure for clear tasks and routine messages. Standard native tree transport is excluded from the second trigger.

The two-workflow grouping is selected for this rollout, not a proven optimum or a prerequisite for other work. One combined internally structured file could be preferable if it reduces missed transitions enough to outweigh extra loading and misrouting. Separate references become useful when substantial conditional detail warrants them; technical content alone is no reason to split.

[Official skill documentation](https://learn.chatgpt.com/docs/build-skills) describes name/description-based selection followed by loading the full body. Internal sections improve navigation but do not automatically remove irrelevant content from the load. Both that cost and the cost of missed invocation belong in the downstream assessment.

## Assessment and disposition

Desk cases covered: rough workflow ideas, a clear typo fix, recipient choice, neutral Claude/Astra comparison, a routine external message, the Pro round trip, user correction/acknowledgment and a returned package. The drafts prescribe observable decisions/results for these cases; they do not force all of them through one checklist.

The selected rollout also installs [harness engineering](../../.agents/skills/harness-engineering/SKILL.md) with a stable name and `metadata.version: "2"`, retaining the former version label without putting it in the invocation name. Version metadata uses the common Agent Skills string mapping; no portable top-level `version` field is assumed. Its design-memory convention is maintained in that skill and applied to the selected packages. The old plugin is disabled in project Codex and Claude settings because partial suppression is not supported consistently across the two surfaces. Unrelated `codex-usage`, `incident-log` and `lesswrong-fetch` capabilities originated as preservation copies; later bounded repairs are recorded separately and [project skill provenance](../../.agents/skills/README.md) records their source. These bounded repairs do not select the semantic adaptations or acceptance programme of the historical [nine-skill migration proposal](../../docs/coordination/skill-migration-plan.md).

[Validation](skill-replacement-validation-20261005.md) records initial structural, link/configuration and byte/mode-preservation checks. At that initial rollout, fresh Codex 0.160.0 discovery passed at the repository root and `thesis/`; fresh Claude 2.1.289 root discovery passed after project settings also disabled the observed `agent-skills@synced` identity. These checks establish discovery, not automatic invocation, reliable application, improved user interaction or thesis benefit. Claude nested-directory discovery and fresh-cloud execution remain untested. No expensive experiment, autonomous thesis programme, global deployment or new transport service was launched.

The selected replacements are installed; retained discovery checks cover the initial rollout. Existing sessions may retain already-loaded entries. One later explicit incident-log trial is recorded in the [incident assessment](../../docs/history/incident-log-evaluation-20261006/README.md), but independent forward evidence for the problem/communication/harness workflows remains absent. The wider workflow-readiness milestone remains open.

On 5 October Jörn identified an unscoped classification instruction as a plausible source of sloppy interpretations reused as facts. The communication body was revised around the actual sending, receiving, choosing, assigning, reporting and integration decisions; unused classification was removed. At that intermediate revision, the full Pro recipe moved to one conditional execution reference; it was subsequently restored inline as described below. This review and structural validation do not establish a behavioral repair.

Jörn further clarified the technical documentation ontology: current channels, tool/script usage, storage paths and formatting/reply contracts should be distinct from strategy guidance and describe the preferred supported path instead of an undifferentiated alternatives catalog. [Technical usage](../../.agents/skills/external-agent-communication/SKILL.md#technical-docs-communication-channels) now covers the observed TUI tools, shell queue, one-shot CLI creation, native neighboring tool contract, human relay and Taildrop. Tool aliases or a dedicated Claude↔Codex bridge are not inferred from their names; unsupported/unverified surfaces are identified. The body now leads with technical docs and contains no single-type classification for multipart messages.

On 6 October Jörn clarified the design sequence and quality/cost asymmetry: build one complete related skill, organize sections usefully, establish useful results, then compare cost-driven decompositions while preserving quality. Substantial quality losses need substantial savings to be worthwhile; restoring capability to a prematurely minimized design is often harder than reducing the cost of a useful baseline. These are his accepted design heuristics, not measured universal facts. Section and file boundaries are distinct decisions. The communication runtime references were folded inline; `references/design-notes.md` remains maintenance-only. The harness now records this sequence and the need to assess reader/maintainer costs rather than infer them from syntax checks. The earlier reference-splitting steps above are superseded; useful behavior and proximity to an optimum remain unestablished.
