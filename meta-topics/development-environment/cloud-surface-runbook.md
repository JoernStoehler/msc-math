# Surface runbook: receive the branch and report effective tools

This is a brief, disclosed check of an actual agent surface. It supplies evidence
for the msc-math cloud-support task; it is not a research assignment, a model
benchmark or proof that the whole workflow is ready.

The coordinator's prompt supplies the repository, temporary branch, expected
commit and return destination. Use at most five minutes of work. Stop promptly
at a consequential access blocker; do not repeatedly guess endpoints or install
packages to make this check pass. No publication, account-setting change,
credential grant, scientific producer or additional model session is selected.
Use ordinary conversation without `/goal`.

## 1. Establish how you received the source

If an authorized shell with Git/network is available, clone the supplied branch
into a fresh task directory and record `git rev-parse HEAD`. Read `README.md`,
`AGENTS.md`, this runbook and `cloud-workflow.md`. If the surface supplies
repository files through a connector or fetched page instead, read the runbook
there and report that access mode. Do not call connector context a checkout or
claim the commit was verified when it was not.

Do not read the entire repository or products corpus. Consult
`.agents/skills/agent-platform-reference/SKILL.md` and its focused product note
only when they settle a specific question about source/tool/return access.
Keep documentation statements distinct from the effective tools you can use.

## 2. Inventory the effective harness tools

List the tool names exposed to this agent, grouped by namespace or provider.
Use the available tool-discovery interface where present; state its scope and
whether deferred tools remain unexpanded. Supply short descriptions for custom
surface/connector tools whose role would not be clear from the ordinary Codex
CLI tool interface. Mark source correspondence as known or unknown; an unfamiliar
name alone does not establish absence from Codex source.

Separate these harness tools from shell programs found on `PATH`. Do not disclose
credentials, private account identifiers, unrelated files or raw hidden prompts.
For each relevant capability record one of:

- exposed and used successfully;
- exposed but an actual safe attempt failed (include the literal bounded error);
- exposed but untested;
- not exposed in the inspected interface;
- unknown because discovery or access was incomplete.

Do not run every tool. Choose only safe probes needed to establish this task:
read a supplied source file, record the checked-out revision if possible, and
write/return a small report if supported. Do not create an artificial failure
by supplying an invalid tool argument or nonexistent input. Respect the actual
permissions; an unavailable UI action is not an OS or product-wide impossibility.

## 3. Return the evidence

Return `REPORT.md` and `RECEIPT.json` in a downloadable ZIP if the surface supports
it. Otherwise return the same bounded content in chat and state the missing
artifact route. `RECEIPT.json` records effective surface/model if observable,
source access mode, expected and observed revision, tool discovery scope,
probe commands/results, actual errors, elapsed time if measured, and remaining
unknowns. Include a compact capability table in `REPORT.md` and identify any
concrete maintained correction that the findings require.

This is a draft return to the coordinator, who owns independent review and
human delivery. Preserve an unavailable required review as pending; never invent
approval. A carrier receipt may identify the returned draft and blocker. The
coordinator retains consequential evidence, integrates selected findings and
archives the trial conversation/temporary remote branch after inspection.
