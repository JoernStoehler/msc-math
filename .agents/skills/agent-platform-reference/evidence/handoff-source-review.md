# Claude chat/Cowork repository handoff: source review

Reviewed 2026-10-13. This review distinguishes Claude chat/Cowork from Claude Code. The two newly acquired Anthropic Help Center pages are stored as direct HTTPS response captures in `evidence/handoff-sources/` (HTML plus extracted text); these are evidence files only and are not added to the corpus manifest.

## Primary sources and exact excerpts

- [Claude Cowork architecture overview](https://support.claude.com/en/articles/14479288), fetched directly from that HTTPS URL; captured as `evidence/handoff-sources/cowork-architecture-overview-14479288.html` and `.txt`. Page title and update status: “Claude Cowork architecture overview”; “Updated this week.” It states: “Cowork sessions run in the cloud by default” and describes cloud execution as an “isolated, temporary sandbox” with one sandbox per session, “created when the session starts and destroyed when it ends.” Cloud sessions have “No access to your network by default.” For device resources, “the request goes through the Claude Desktop app on that device”; “Local file access is limited to folders the member has connected on the desktop”; if the desktop app is offline, a cloud session “can't reach the device.” Existing local sessions are a different mode: “The agent loop runs natively on the device”; “Code execution runs in an isolated virtual machine (VM).” The article says the same architecture applies across plans, while identifying which local deployments remain available.
- [Organize your tasks with projects in Claude Cowork](https://support.claude.com/en/articles/14116274), fetched directly from that HTTPS URL; captured as `evidence/handoff-sources/cowork-projects-14116274.html` and `.txt`. Page title and update status: “Organize your tasks with projects in Claude Cowork”; “Updated over 3 weeks ago.” It says projects have “their own files, context, instructions, and memory,” and “New projects you create in Cowork are saved to your Claude account”; “projects you create from a folder on your computer stay on that computer.” The documented creation routes are “Start from scratch,” “Import from a Claude project” (the page notes “bulk upload is not supported”), and “Use an existing folder on your computer.” Cowork projects can add instructions, local folders, linked chat projects, and URLs as context. Current limitations: “Projects you create from an existing folder on your computer stay on that computer and aren’t saved to your Claude account.”
- [Use Claude Cowork on web, desktop, and mobile](https://support.claude.com/en/articles/15520349), local mirror `corpus/articles/anthropic/claude-chat/claude-chat-cloud-cowork.md`. This provides complementary execution and surface details: a cloud session reaches only folders connected on the computer through Desktop, while the app is open; cloud file access fetches copies of requested files. It explicitly links the new architecture and project help pages. It says “Projects tied to a local folder support Cowork sessions on desktop only.”
- [How can I create and manage projects?](https://support.claude.com/en/articles/9519177), local mirror `corpus/articles/anthropic/claude-chat/claude-chat-projects.md`. Ordinary chat Projects use an uploaded knowledge base and project instructions; the document says files uploaded there are used as context across project chats. This is a separate route from a Cowork project backed by a local folder.
- Claude Code is separate. Local reference `references/claude-code.md` points to official Claude Code memory and Skills documentation for `CLAUDE.md`, `AGENTS.md`, and filesystem skill paths. Those are Claude Code mechanisms and do not establish automatic loading by chat or Cowork.

## Handoff implications for the repository example

A portable handoff should make its contract explicit in repository files: identify required inputs, outputs, commands, and expected result; give Claude a direct instruction to read the bootstrap/documentation entry point first; keep dependencies and runnable demo assets inside the repository or installable from its declared lock/config files. A commit pushed to a remote gives a stable, nonlocal handoff reference, but the cited Cowork Projects article documents selecting an existing local folder, importing a Claude chat Project, or starting from scratch. It does not document cloning a Git repository or adding a GitHub repository as a Cowork project source. Therefore describe remote clone/import as a user-mediated setup step unless another current primary source explicitly documents it. A Claude GitHub connector may provide repository context in chat, but that does not itself establish a Cowork project checkout or writable working tree.

For a local-folder Cowork project, the folder stays on that computer; access from cloud sessions is constrained to connected folders via the online Desktop app. The architecture page documents code execution in a VM but does not specify a host-visible path mapping, a persistent home directory, or a Cowork project path convention. Do not claim a stable VM home/path or that dependencies installed outside the repo will persist across sessions. For predictable reruns, include dependency declarations, lockfiles, and setup instructions in the repo and make bootstrap installation repeatable. Cloud sandboxes are session-temporary, so avoid treating their VM filesystem as durable project storage.

Neither architecture nor Projects help page documents a port-forwarding mechanism, a preview URL for a local web server, or a UI that presents localhost ports. “Preview files Claude creates” in the surface article is not evidence of arbitrary web-server port presentation. If the handoff requires a usable demo, provide a pushed commit and a nonlocal hosted webdemo URL/deployment path, or explicitly state that local port exposure is an unverified manual step. Keep the repo’s run instructions and the hosted demo URL together so the handoff remains portable.

## Claims unsupported by these sources

- Cowork automatically reads `CLAUDE.md`, `AGENTS.md`, or `.claude/skills/` from a selected folder. Those are Claude Code-specific mechanisms in the references; no reviewed chat/Cowork source promises their automatic ingestion.
- Cowork Projects clone, pull, or push Git repositories, or offer a “GitHub Add” flow. The Projects article lists folder selection, Claude Project import, and scratch creation only. Repository connectors and local project folders must not be conflated.
- Cloud Cowork has persistent VM home storage, a documented repo path, or dependencies persist between sessions. The architecture source instead calls cloud sandboxes temporary and destroyed at session end.
- Cowork exposes localhost ports, automatically publishes local web servers, or embeds a project’s running app. No reviewed source specifies port presentation or local port forwarding.
- A connected local folder is equivalent to uploading a repository to account-level Cowork storage. Sources describe distinct folder-backed local projects and account-saved Cowork projects.

These are documentation findings, not a live test of any account, rollout, connector, or desktop runtime.
