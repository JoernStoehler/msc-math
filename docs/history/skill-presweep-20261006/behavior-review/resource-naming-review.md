# Resource decomposition and CLI naming review

6 October 2026. Read the actual `codex-usage` SKILL.md, bootstrap script and run wrapper, plus its maintenance notes; reused the independently read complete `codex-resources` candidate. No active files, accounts, models, network, configuration or schedules were changed. No resource naming recommendation report was read. **Independence limit:** the CLI maintenance notes already contain the suggested name `codex-cli-from-claude`; this naming judgment is therefore informed, not blind. The complete-versus-split comparison was formed from the candidate's content and current workflow, not a parent recommendation.

## Retain one complete resource baseline first

Prefer the single `codex-resources` candidate as the first useful baseline. Inventory, allocation, redemption and scheduled recovery are adjacent stages of one resource decision. Their shared distinctions—account quota versus attribution, observation versus authority, selected credit versus backend choice, scheduled start versus completed outcome—are needed at transitions where splitting increases missed discovery and retrieval risk. The candidate already has useful internal sections; it is not necessary to create parallel tracking and reset packages to expose those sections.

A tracking/reset split has a real alternative benefit: frequent read-only checks could load fewer redemption and persistence details, while rare consequential actions could load their own complete workflow. It would also create two discovery descriptions, caller migrations and maintained boundary statements. A tracking return that discovers imminent expiry would need to select the reset skill without converting urgency into action authority. Compare that actual transition and maintenance burden before splitting; filenames alone establish neither cost savings nor better behavior. No measured loading cost or behavioral superiority is claimed here.

The single baseline should not absorb ordinary CLI bootstrap or delegation. That consumer has different effects, prerequisites, secrets boundaries and completion conditions. This is a distinct workflow, not merely another resource section.

## Name the existing workflow for its actual consumer

Recommend **`codex-cli-claude-cloud`**, with an opening description such as: “Set up and run bounded Codex CLI tasks from a Claude cloud session; handle authorized installation/output sharing and per-grant login, then collect the final result and execution evidence.”

The current package installs the CLI when needed, optionally links session outputs into `/mnt/attach/outputs`, handles separately authorized device authentication, and runs a timed `codex exec` wrapper with final output and event logs. It does not inspect quota, track spending or redeem resets. The cloud qualifier preserves the tested/preserved surface rather than promising support from every Claude context. `codex-cli-from-claude` is shorter and defensible if a broader Claude-to-CLI consumer is intentionally supported; the inspected evidence currently favors the narrower name. `codex-usage` does not discriminate this workflow from account usage and resources.

A rename must migrate the directory/name, root heading, script instructions that mention `codex-usage SKILL.md`, discovery entries and maintained callers. The wrapper's missing-CLI advice must continue to mean authorized setup, not a new install permission. Naming does not change login authority or establish current cloud compatibility. Root owns any actual migration and activation.

## Is the resource baseline missing consequential content?

No additional authority or decision-content gap is apparent from this bounded review. The candidate covers minimal observation, telemetry limits, existing authorization, selected credit preservation, ambiguous-operation reconciliation, post-consume refresh, refusal versus final disposition, durable schedule verification, receiving/recovery ownership and user cutoffs. It preserves the withdrawn eligibility advice and does not invent authority from capacity.

There **is an explicit executable capability gap**: no selected scheduler, persistent recovery controller or private selection-preserving redemption adapter is supplied. The candidate itself exposes that limit rather than hiding it. This prevents an unqualified redemption/scheduling promise, but need not prevent a useful baseline for resource checks, allocation reasoning and identifying a missing execution route. Assess those observable results separately from successful reset execution. If the intended baseline must actually redeem or recover after the initiating turn ends, verify/build that mechanism within the existing authorization before claiming that capability; another wording revision cannot supply it.

These conclusions warrant a deliberate naming migration and a complete resource baseline review, not a claim that the candidate is activated, behaviorally validated, or ready to execute every supported action.
