# AI-Use Provenance

This folder owns the evidence packet for thesis AI-use provenance. It supports
two distinct thesis consumers: the factual front-matter disclosure and section
13's discussion of AI-assisted mathematical research. It also supports
PaperOrchestra inputs. The packet supports interaction-provenance claims; it
does not prove mathematical correctness or measured research impact.

The current committed report is
[`reports/ai-provenance-log-backed-summary.md`](reports/ai-provenance-log-backed-summary.md).
It is a log-backed interaction-provenance model over available Codex and Claude
session archives. Treat it as evidence for who steered, drafted, implemented,
reviewed, accepted, or rejected work in the inspected sessions. Do not use it
as source truth for theorem correctness.

The repo-facing report intentionally keeps the aggregate model and per-area
classification, not the detailed per-session summaries. Detailed transcript
tables are scratch investigation artifacts; raw logs remain the source evidence
when a later refresh needs to re-check them.

## Motivation

The thesis needs an honest account of AI use that is stronger than memory and
more specific than git history. Git can show which files changed, but it does
not reliably show who supplied an idea, who rejected a false draft, who accepted
a proof route, or whether a piece of code/prose was generated by an agent and
then reviewed by Jörn.

The target object here is therefore an empirics-based provenance model:

- what kinds of labor AI agents performed;
- what kinds of steering, correction, mathematical judgment, and acceptance
  Jörn supplied;
- where Kai/Elizabeth/literature/executable verification enter the story;
- which authorship/origin questions remain uncertain and must stay uncertain in
  thesis prose.

This packet is also an input-control surface for PaperOrchestra. A paper-writing
workflow should not invent AI-use provenance from style, file ownership, or
generic assumptions. It should use the aggregate report here and preserve its
uncertainties.

## Methodology

The source evidence is interaction history, not repository state. The
investigation used Codex rollout logs and Claude transcripts to classify
chat-level provenance. The useful evidence types were:

- Jörn user messages: goals, constraints, corrections, approvals, rejections,
  taste calibration, mathematical questions, and statements about offline/Kai
  context;
- assistant final or user-visible messages: what agents claim to have written,
  implemented, reviewed, tested, or left uncertain;
- subagent completion summaries when present: compact evidence about delegated
  review or extraction work;
- import/inventory counts: coverage evidence for which log archives were
  visible.

The synthesis step was intentionally not a deterministic parser. It is an
LLM-assisted classification task over noisy human/agent transcripts. The
scripts support reproducibility by inventorying logs and checking cited paths,
but the classification itself still needs a capable agent and human review.

The committed report keeps the useful abstraction layer:

1. thesis-wide executive model;
2. per-area Jörn-vs-AI contribution classification;
3. imported Claude/pre-Codex update;
4. comparison against the scratch interview worksheet;
5. open questions for Jörn.

Detailed per-session tables are not committed. They are too large and too close
to raw transcript data for ordinary repo use. If needed, regenerate them in
scratch space from the prompt and logs.

## Trust Boundary

- Raw session logs under `/home/vscode/.codex` and `/home/vscode/.claude` are
  the source evidence.
- The report is an LLM-authored synthesis from those logs, not a deterministic
  derivation.
- The scripts in `scripts/` inventory available logs and check that cited
  evidence paths exist. They do not replace the LLM/human synthesis step.
- Git history is not evidence for idea provenance.
- User messages are evidence for what Jörn provided in chat, but not a complete
  record of offline thinking or meetings.
- Assistant messages are evidence for what AI produced or attempted, but not by
  themselves evidence that Jörn accepted the output.

## Commands

Inventory visible logs:

```bash
python3 experiments/ai-use/scripts/collect_log_inventory.py \
  --out experiments/ai-use/artifacts/log-inventory.json
```

Check the current report's cited evidence paths:

```bash
python3 experiments/ai-use/scripts/check_report_evidence.py \
  experiments/ai-use/reports/ai-provenance-log-backed-summary.md \
  --out experiments/ai-use/artifacts/report-evidence-check.json
```

Check the scripts themselves:

```bash
python3 -m py_compile experiments/ai-use/scripts/*.py
```

Diagnose recorded Codex usage and cache reuse:

```bash
uv run --script experiments/ai-use/scripts/analyze_token_usage.py \
  --start 2026-07-04 --end 2026-07-12 \
  --out-dir /tmp/codex-token-usage --plot
```

For the full visible archive, add the imported root and use monthly plotting:

```bash
uv run --script experiments/ai-use/scripts/analyze_token_usage.py \
  --start 2025-09-01 --end 2026-07-12 \
  --root /home/vscode/.codex/sessions \
  --root /home/vscode/.codex/archived_sessions \
  --root /home/vscode/.codex/imported_session_logs \
  --out-dir /tmp/codex-token-usage-lifetime \
  --plot --plot-bucket month
```

The producer writes daily, model/effort, lineage, rollout-level, and
API-equivalent shadow-cost CSV files, plus `summary.json` and an optional
`token-usage-overview.png`. It groups by
the UTC timestamp of each raw `token_count` event, uses `last_token_usage`,
and skips duplicate records whose cumulative usage is unchanged. The output is
diagnostic evidence, not a billing estimate or a causal measure of research
impact; do not add it to the thesis without a separate reader/use decision.

The project-efficiency producer consumes those CSV outputs and adds a separate
month-end Git snapshot table. Its resource totals are generated; semantic value
assessments live in the canonical report and are not inferred from line count.

The last smoke run before committing this packet found 5,880 visible Codex and
Claude logs in the local environment and wrote the inventory to `/tmp`, not to
the repo.

## Refresh Workflow

Use this workflow when the provenance model needs to be updated:

1. Ensure the relevant Codex/Claude logs are visible in `/home/vscode/.codex`
   and `/home/vscode/.claude`. If logs were copied in from the host, update the
   import report or add a new dated import report.
2. Run `collect_log_inventory.py` to record local coverage in ignored
   `artifacts/` or `/tmp`.
3. Start a new Codex session with
   [`prompts/ai-provenance-investigation-prompt.md`](prompts/ai-provenance-investigation-prompt.md).
   The prompt asks the agent to inspect chat-level provenance, merge it into an
   aggregate model, and avoid committing per-session evidence tables.
4. Review the produced report for overclaims. In particular, check that
   unresolved idea origins remain marked as mixed or uncertain.
5. Replace `reports/ai-provenance-log-backed-summary.md` with the reviewed
   aggregate report.
6. Run `check_report_evidence.py` and `python3 -m py_compile` before committing.

## Interpretation Rules

- Do not convert "AI wrote or edited substantial code" into "Jörn did not
  understand or trust the result". Trust is established separately by tests,
  exact verification, mathematical review, and thesis acceptance.
- Do not convert "Jörn asked for X" into "Jörn first invented X". Chat logs do
  not exhaust offline thinking.
- Do not convert "assistant produced X" into "X was accepted". Acceptance needs
  user approval, later use, tests, or other supporting evidence.
- Do not flatten "AI use" into one category. Code generation, proof-risk
  review, literature search, orchestration, data-science interpretation, and
  final prose drafting have different disclosure implications.
- Do not promote worksheet guesses into facts unless the log-backed report or
  later Jörn correction supports them.
