# Goal loop and human-input source review

**Pinned source:** `benchmark-run/shallow`, tag `rust-v0.162.1`, commit `092d3acd6bec3e3a14bdc7e7a2810ab628ab759d`. The source excerpts and source/excerpt SHA-256 values are in `evidence/goal-source/provenance.json`.

## What the pinned source says

The built-in slash parser accepts a command only when the first character is `/`; its shape is `/name <rest>` (`slash-only-parse.rs`). `/goal` is described as setting or viewing a long-running task goal (`goal-command-name.rs`). The slash dispatcher handles `/goal <objective>` as a goal draft, and `/goal pause`, `/goal resume`, `/goal clear`, and `/goal edit` as controls (`goal-slash-dispatch.rs`). Therefore plain text such as `Goal: ...` is not itself the TUI `/goal` command. The model-facing `create_goal` tool separately says to create a goal only when explicitly requested and not to infer goals from ordinary tasks (`goal-tool-policies.rs`). This is a source instruction, not proof of how a particular workstation run interpreted the user's prompt.

When a thread becomes idle, the goal extension calls `continue_if_idle` (`idle-goal-continuation.rs`). That method checks the persisted goal and starts another turn when status remains `Active` (`goal-continuation-runtime.rs`). At turn completion, the TUI emits the ordinary `AgentTurnComplete` notification only if no queued follow-up started and the current goal is not active (`turn-complete-notification-gate.rs`). Together these source paths explain why an active goal can continue without the normal end-of-turn notification that would signal the agent is waiting for the user.

The continuation template tells the agent to keep an incomplete goal active while making progress, report a genuine blocker and keep the goal active until the blocked audit threshold is met, and mark it blocked only after the same blocker recurs for at least three consecutive goal turns and the agent cannot make meaningful progress without user input or external change (`goal-continuation-hard-blocker-guidance.md`, `goal-blocked-pause-audit.md`). Thus a missing prerequisite can be a genuine hard blocker in principle, but one occurrence is explicitly insufficient for `blocked`; the goal continuation machinery itself has no automatic first-blocker suspension. A separate `request_user_input` route can wait within an active turn in Plan mode when the feature is enabled; see `human-input-source-review.md` for its feature and mode conditions.

There are human controls. The slash dispatcher sends a status update for `/goal pause` (`goal-slash-dispatch.rs`). During an interrupt, `pause_active_goal_for_interrupt` sends `Paused` if the goal is active and its turn is running (`interrupt-pauses-active-goal.rs`). The goal tool instructions also state that `paused` requires an explicit user request and says never to pause on the agent's own initiative (`goal-tool-policies.rs`). These are exposed controls, not evidence that the user's reported session used one.

## User report and verification boundary

The user reports that, on their workstation about five minutes before reporting, the prompt `Goal: bla bla` triggered a `/goal` loop, end-turn did not ping while the loop was active, the loop instructions said not to end until completion, and the agent continued despite lacking required information because asking appeared to require ending the goal and turn. The missing end-turn notification and repeated active-goal continuation are consistent with the pinned source paths above. The report that this exact plain-text prompt activated a goal is not explained by the built-in slash parser; the model-facing tool policy says not to infer a goal from ordinary tasks, but this review did not run or inspect that workstation session. It may reflect model interpretation, configuration, or source differences, and remains an observed report rather than a generalization. No inference or runtime test was run here.

## Consumer implications

For an optional clarification, keep unrelated work moving and do not force every active goal to exit. For a hard prerequisite that prevents any meaningful next action, state the missing information clearly and use the available user-facing path; do not invent an answer or imply that the user replied. In this pinned version, the goal loop's normal end notification is suppressed while status is active, but distinct question notifications and an in-turn blocking `request_user_input` route exist (subject to current mode, feature flags, and notification settings; see `human-input-source-review.md`). Ordinary `request_user_input_async` is nonblocking by design (see the companion async-question source review). The explicit goal pause controls remain user-directed `/goal pause` or pausing when an interrupt is issued; `update_goal(paused)` is forbidden without an explicit user pause request. `blocked` is a later audited disposition after the same blocker recurs for three consecutive goal turns, not an immediate pause switch.
