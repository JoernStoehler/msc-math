# Workflow discussions — 10 October comparison

Historical research comparison, retained from 337f on 12 October. Recommendations were not selected for execution. Source claims have not been re-audited during integration; the current topic owners supersede this dated snapshot. Paths in code spans retain historical source identity.

The strongest discussions support **preparing an executable handoff and a recoverable repository**, while treating the choice to start a fresh session as model- and task-dependent. I found five substantive primary accounts; none tests the proposed workflow on our current models or a brownfield scientific thesis repository.

1. **Anthropic, Justin Young, 26 November 2025: [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents).** This is the closest analogue. An initializer prepares the environment, feature list, startup script, progress record and Git baseline; subsequent coding sessions implement one feature and leave verified progress. Its failures include premature victory, broken environments and undocumented work. The handoff therefore transfers runnable state and completion criteria, beyond a polished prompt. Coverage is principally full-stack web application development; the later account identifies Sonnet 4.5 as the original harness model. The authors explicitly leave open whether generalist or specialist architectures perform best and describe scientific applications as future generalization, not demonstrated results.

2. **Anthropic, Prithvi Rajasekaran, 24 March 2026: [Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps).** Particularly valuable because it revises the earlier recommendation. Sonnet 4.5 needed resets; Opus 4.5 allowed continuous sessions with compaction; Opus 4.6 allowed removing sprints. The planner specifies deliverables while avoiding granular technical prescriptions that could cascade into implementation errors. Generator and evaluator negotiate testable sprint contracts. This supplies concrete decision rights: the planner sets product scope, implementation details emerge during execution, and evaluation tests the contract. One illustrative Opus 4.5 comparison cost $200/6 hours against solo $9/20 minutes, but the planner expanded scope, so it does not isolate architecture or establish cost-effectiveness. Evaluation required tuning and still missed bugs. Those limits make this a useful discussion rather than an unqualified success claim.

3. **OpenAI, Ryan Lopopolo, 11 February 2026: [Harness engineering](https://openai.com/index/harness-engineering/).** A five-month internal Codex engineering account, starting with an empty repository. It emphasizes versioned execution plans, decision logs, architecture maps, executable checks and an environment that boots per worktree. Knowledge outside the repository is effectively unavailable to agents; documentation must be indexed, maintained and checked for staleness. This supports doing disruptive preparation once and leaving durable infrastructure that later sessions can inspect. It does **not** establish that separate preparation and execution sessions outperform continuity. The estimated development speedup is an uncontrolled team estimate; specific model versions and a matched comparison of session structures are absent.

4. **Cursor, Wilson Lin, 5 February 2026: [Towards self-driving codebases](https://cursor.com/blog/self-driving-codebases).** The most useful counterexample to rigid plan-then-execute. Initial detailed planning with Opus 4.5 failed; manually distributed subtasks increased throughput without much better results. A planner→executor→judge pipeline improved accountability but was bottlenecked by the slowest worker and could not promptly revise discoveries. Combining every responsibility in one continuous executor then produced overload and premature completion. Their eventual design used continuing planners and bounded workers; worker handoffs included deviations, concerns and findings, letting planning respond to the updated repository. Models included GPT-5.1/5.2. Coverage was an experimental browser, with deliberately tolerated intermediate errors. This is evidence about observed coordination failures, not a recipe for accepting unchecked mathematical claims.

5. **Anthropic Applied AI, 29 September 2025: [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).** A complementary engineering synthesis: compaction preserves architectural decisions and unresolved bugs but can discard subtle context; persistent notes support milestones; specialists isolate deep exploration and return condensed results. It recommends continuity for extensive back-and-forth, notes for iterative work, and specialists where parallel exploration pays. It also discusses the tradeoff between prepared retrieval and slower runtime discovery. Coverage spans Claude Code, research and other long tasks; this article offers mechanisms and engineering judgment, rather than a controlled comparison of all architectures.

**Recommendation for the ongoing agenda — an inference from these accounts:** use the proposed preparation→fresh execution pattern when preparation materially changes the repository’s structure, setup or working conventions. The preparation session should produce a small retained package: inspected baseline, tested setup commands, source/evidence map, rationale for scope choices, dependencies, unresolved uncertainties, and a first bounded work unit with explicit completion evidence. A prompt alone leaves hidden setup and nonportable knowledge unresolved.

Keep scientific scope and resource decisions with Jörn and the coordinating owner. Give execution authority over routine implementation, plus an explicit route to revise a stale plan when evidence contradicts it. Organize homogeneous sprints where they reduce switching between proof, infrastructure and prose; the sources do not justify making sprints mandatory.

Continue in the same context while mathematical rationale is still forming through conversation. Use bounded specialists for independent source checking or technical investigation, with retained evidence behind their summaries. The practical tradeoff remains unmeasured here: fresh execution reduces accumulated conversational baggage but costs reorientation and risks losing rationale; continuity preserves nuance but can accumulate obsolete assumptions.
