# Research execution capabilities

**Reviewed:** 2026-10-13 against the locally acquired product documentation and the current Codex agent-tool surface. Use this page when a long research session has become serial, overloaded, or weak at checking its own conclusions. It is a capability lookup for diagnosis and intervention choice, not a default instruction to parallelize every research task.

## Start with the failure mode

For the disclosed BSc-scale theoretical mathematics example, the symptoms were a long serial chain, one overloaded context, and sanity checks falling away. Separate those into decisions: whether there are genuinely independent subquestions; whether source reading or intermediate derivations are crowding out the synthesis context; whether each line of work needs the same model and reasoning effort; and what explicit cross-check would make the final result more reliable. If the proof is dependency-heavy, keep it serial and use bounded side work only for independent lemmas, counterexample search, or verification. Extra agents add token and coordination costs and do not establish mathematical correctness. OpenAI's Codex subagent docs say workers cost more tokens and describe the benefit as moving noisy exploration off the main thread ([C1]); Anthropic similarly says teams use significantly more tokens and work best when teammates can operate independently ([A1]).

Consult this reference at concrete moments: after repeated context overflow or compaction, when raw exploratory material is displacing the theorem statement and assumptions, when one branch can be checked independently, when selecting model/effort for a demanding derivation versus a fast scan, when deciding whether isolation is needed for edits, or when deciding how to retain and inspect evidence. A good intervention can be a short structured checkpoint, a new focused session, a proof ledger, one independent critic, or no delegation at all. Pick the smallest lever matching the diagnosed failure.

## OpenAI Codex surfaces

Do not transfer capabilities between ChatGPT ordinary chat, ChatGPT Work, and Codex CLI/IDE/desktop. The acquired Work docs distinguish hosted Work subagents from local Codex clients; availability and controls depend on the surface and account. The current conversation's enabled tool schema is itself a runtime-specific affordance: `collaboration.spawn_agent` exposes `model` and `reasoning_effort` options here, while a different client may not. Documentation is not proof that a feature is enabled in a particular account. Check current tool discovery, client/version, selected model, and account access before prescribing a control.

In current Codex app/CLI/IDE docs, explicit subagent requests and applicable project/skill instructions can trigger parallel subagents; the main agent routes work, collects results, and can inspect threads. Model and reasoning effort may be inherited or explicitly configured; documentation names `model` and `model_reasoning_effort`, and `[agents]` defaults including `default_subagent_model`, `default_subagent_reasoning_effort`, and `max_concurrent_threads_per_session` ([C1]). These are documented configuration fields, not a promise that every runtime exposes them. In this Work Mode runtime, the callable collaboration schema lists model overrides and reasoning-effort overrides, but no explicit per-call concurrency parameter; do not infer a universal maximum. Any numeric cap must come from the active client docs/config or tool inventory, not guesswork.

Subagents can reduce main-thread context load when they return concise evidence instead of transcripts. They can also introduce inconsistent assumptions or lose shared derivation context. Partition by independent question, specify the common definitions/assumptions and requested evidence, and reunite results in a proof ledger. Keep the main thread responsible for integration and verification. For serial dependencies, ask for a lemma or intermediate artifact and wait before assigning dependent work.

Codex worktrees address repository isolation for multiple chats/edits; the documented desktop implementation uses Git worktrees, and a worktree is a separate checkout sharing Git metadata ([C2]). This matters when research includes reproducible code, symbolic experiments, or note edits. It is not a context-window remedy and does not improve a pure derivation by itself. Worktree availability and lifecycle differ by client.

For observability, Codex's acquired skill-evaluation documentation says JSONL traces can include `turn.completed` usage and `usage.input_tokens` / `usage.output_tokens`; Codex AGENTS docs describe an opt-in TUI log and session JSONL when session logging is enabled ([C3]). Treat those as local Codex CLI evidence paths, not standard ChatGPT chat telemetry. This corpus does not establish a generally available live per-thread context meter for every Codex surface. Prefer what the active UI exposes; when investigating a CLI run, inspect only logs the client has actually been configured to write.

Quota visibility is another surface-specific question. The acquired Codex app-server reference documents `account/rateLimits/read` and `account/rateLimits/updated`, with fields such as `usedPercent` and quota-window duration ([C4]). These are app-server protocol methods, not a user-facing command guaranteed in every client. Check the active product/account limits instead of assuming subagents have a separate quota or multiplying an account cap by worker count.

Context pressure and compaction are separate from task rollover. Compaction summarizes/replaces accumulated conversation state to continue in the same session; starting a fresh session or handing off creates a distinct work context and requires a deliberate checkpoint of definitions, claims, proof status, and open objections. A source in this corpus gives detailed compaction mechanics for Claude Code, not a universal Codex contract. Do not promise identical compaction thresholds, preserved history, or rollover behavior across Codex clients without a surface-specific source.

## Anthropic surfaces: Claude Code is not Claude chat

The acquired Anthropic docs distinguish Claude Code CLI/Desktop/cloud from ordinary Claude chat and Cowork ([A2], [A3]). Claude Code subagents run in separate context windows, can have scoped tools/permissions, and return summaries; subagents consume the same plan usage limits as the main conversation ([A1]). A subagent definition supports `model`, `effort`, and `isolation: worktree`; the available effort levels and model choices depend on the selected model and installed/versioned client ([A1]). Agent teams add direct teammate messaging and shared task coordination, with additional token/coordination overhead; use that only when workers need to coordinate or challenge one another, not as a synonym for a subagent ([A4]).

Claude Code documents `/context` for a live category breakdown, `/compact` for reducing session context, JSONL session transcripts, and structured usage/cost results for non-interactive calls; its OTel monitoring docs expose model, effort, and token/cost attributes ([A5], [A6], [A7]). These are Claude Code controls and records. Claude chat has Projects, project instructions/knowledge, chat Skills, and account personalization with plan/rollout variation, but the acquired Claude chat docs do not establish Claude Code's Agent tool, subagent context isolation, worktrees, `/context`, `/compact`, or Code JSONL/OTel observability in ordinary chat ([A3]). Do not suggest invoking Code-specific commands from Claude chat. If the user means chat, diagnose with the actual chat surface's context/project features and use fresh chats/checkpoints as available.

## Selecting an intervention after diagnosis

For a case like the disclosed mathematics example, first state the result sought, definitions, assumptions, and proof dependencies. Then choose genuinely separable tasks with concurrency matched to the critical path, available quotas and verification needs—for example, a targeted search for counterexamples and an independent check of one key lemma—while retaining the main line of proof in the primary context. Give each worker a bounded question and require a short result with assumptions, derivation or source, and uncertainty. Reconcile disagreements explicitly, rerun the sanity checks, and record a compact checkpoint before the next phase. This is a suggested intervention inferred from the cited capabilities and the user's disclosed example, not a vendor guarantee or rule that more agents improve research.
