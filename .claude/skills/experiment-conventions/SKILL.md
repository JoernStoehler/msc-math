# Experiment Conventions

## Directory Layout

```
experiments/
  Cargo.toml             Builds all experiment Rust binaries (depends on symplectic crate)
  reproduce.sh           Source of truth for full pipeline (zero data → thesis PDF)
  IDEAS.md               Research directions, priorities, deferred ideas
  <name>/                Per-experiment folder
    logbook.md           Living document: motivation, attempts, interpretation, ideas
    run.rs               Rust binary source
    analyze.py           Python analysis script
    data.jsonl           Dataset (generated by Rust binary)
    *.png                Figures (generated by Python script)
    README.md            Operational: files table, how to run, status
  requirements.txt       Python dependencies
```

The folder name provides the namespace. Files inside use role-based names (`run.rs`, `analyze.py`, `logbook.md`), not `<name>.rs`, `<name>.py`, `<name>.tex`.

**Legacy:** Existing experiments still use `<name>.rs` etc. New experiments use the role-based names. Rename old files opportunistically when touching them.

## The Logbook

The logbook (`logbook.md`) is the primary document for each experiment. Everything goes here: motivation, what was tried, what the results mean, dead ends, open questions, deferred ideas, blockers.

**Agents read the logbook first** when starting work on an experiment. It tells you why the experiment exists, what's been tried, what's worth pursuing next.

**Agents write into the logbook** as they work. Not after — during. Record decisions, results, interpretations, surprises, and abandoned directions with enough context that a future agent (or Jörn) can pick up without re-deriving everything.

### What goes in the logbook

- **Motivation:** What thesis question does this experiment address? Why does it matter?
- **Attempts and outcomes:** What was tried, what happened, what the data showed
- **Interpretation:** What the results mean for the thesis argument. Label speculation as interpretation.
- **Dead ends:** What was tried and abandoned, and *why* — so future agents don't retry it
- **Deferred ideas:** Directions paused with resume conditions ("worth revisiting if we get F>12 data")
- **Open questions and blockers:** What's unclear, what's needed to proceed
- **References to data/figures:** "The histogram (data.jsonl, analyze.py) shows bimodal distribution at F=8"

### What does NOT go in the logbook

- Reproduction commands → README.md
- File listings → README.md
- Code documentation → code comments
- Raw data → .jsonl files
- Thesis-quality prose → .tex (extracted from logbook when story is clear)

### Staleness convention

Logbook entries grow stale as the experiment evolves — old interpretations get superseded, figures get regenerated. This is fine. Old entries are kept so context isn't buried in git history. The current state is whatever's at the bottom / most recent. Old data and figures referenced by stale entries live in git history.

Don't update old entries to match new figures. Don't delete old entries. Just add new ones.

## README.md

Operational metadata only. No findings, no interpretation — that's in the logbook.

```markdown
# {Title}

{1-2 sentence: what question does this answer?}

## Status
{Complete | In Progress | Blocked | Abandoned (see logbook)}

## Files
| File | Purpose |
|------|---------|

## Run
```bash
{reproduction commands}
```
```

## Thesis Extracts (.tex)

The .tex file is a thesis section *distilled from* the logbook. It is not written until the story is clear. It contains polished, self-contained prose for thesis readers — not a data dump.

**When to write .tex:** When the experiment has findings worth presenting in the thesis and Jörn has indicated what role those findings play in the thesis argument.

**How to write .tex:** Extract the key findings and interpretation from the logbook. "Write up what's there — nothing more, nothing less" applies to the logbook content, not to raw data. The .tex should have a *point* — what does this show for Viterbo's conjecture?

## Pipeline Direction

Rust binary → .jsonl → Python script → figures/tables → thesis

**No circular dependencies:**
- Python never calls Rust directly
- Rust binaries are built from `experiments/Cargo.toml` (`cd experiments/ && cargo build --release`)
- To add a new experiment: create `<name>/` folder, add `[[bin]]` entry to `Cargo.toml`, update `reproduce.sh`

`experiments/reproduce.sh` documents the full pipeline from zero data to compiled thesis. It is the single source of truth for reproduction. When adding, removing, or changing an experiment, update `reproduce.sh` to match.

## Data and Figures in Git

**Tracked (committed):**
- `experiments/<name>/*.jsonl` — datasets generated by Rust binaries
- `experiments/<name>/*.png` — figures generated by Python scripts
- `experiments/<name>/*_output.txt` — stdout from binaries whose deliverable is stdout

**Regeneration:**
- Regenerate on the branch that changes the code. Data should match the code that produced it.
- Separate commits for code changes vs data regeneration.

**Merge conflicts (data/figures):** Resolve by regenerating on the merged result.

## Philosophy

Experiments are always investigative — even mature ones remain open to revisiting, expansion, and updating.

**Exercise judgment about priorities.** Before starting work on an experiment, check IDEAS.md and TASKS.md. If the current direction seems low-value compared to alternatives, say so and propose switching. Don't mechanically complete work that no longer matters.

**Record abandoned directions.** When pausing or abandoning a direction, write in the logbook: what was tried, why it was abandoned, and under what conditions it would be worth resuming. "Deferred" ≠ "dropped."

## Library Imports

Stable, shared code lives in `crates/` and experiments import it. Common imports:
- `symplectic::Polytope4D` (or `symplectic::geom::polytope::Polytope4D`)
- `symplectic::ehz_capacity`, `symplectic::billiard_capacity`
- `symplectic::volume`, `symplectic::omega0`
- `symplectic::known_polytopes`

Only stable, proven code goes into `crates/`. New algorithm variants stay self-contained in experiment binaries until promoted to production.

## Quality Standards

**Rerunnable from zero:**
- Starting from empty experiment directories, running all scripts should reproduce all outputs
- No manual steps, no "run this once, then comment it out"

**Document assumptions:**
- If script assumes file exists, document it in header and error message

**Not production code:** No exhaustive testing required, but must be reproducible. Focus on clarity and correctness over performance.

## Writing Rules

**Write up what's there — nothing more, nothing less.** Report what the data shows. Facts are facts, correlations are correlations, unknowns are unknowns. Speculation must be explicitly labeled as interpretation.

- Every factual claim must be verified against the actual data (JSONL) in the same session
- When verification is impossible, mark with `% [TODO: JÖRN -` or `% [GAP -`
- Agent-generated figures and writeups are drafts until Jörn reviews
- Statistical claims require reproducible computation

## Self-Review Before Presenting

Before presenting any experiment deliverable to Jörn, dispatch a subagent to re-read the logbook and .tex with these questions:
1. Does the logbook explain *why* this experiment exists?
2. Does the .tex have a *point* (not just "here's what we measured")?
3. Are all factual claims verified against data?
4. Are there other experiments or directions that would be higher value right now?
