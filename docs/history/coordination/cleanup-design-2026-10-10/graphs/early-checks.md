Jörn considers the overall package worth running and asks what can be learned
before paying for the bulk. The main change is an early complete example,
not a new global preparation phase. Execution timing below is a proposed
checkpoint, not a measured runtime or an overnight launch.

## 1. Does the account enable useful writing, not only a plausible plan?

**Move from final assembly to the first completed hard topic slice; target the
first execution hour.** Use the DS ridge/selection/transfer story, where existing
human feedback exposed missing organization, unsupported explanatory links and
unclear scientific terms. Do not use the already-polished pentagon proof as the
main test. Relevant owners are the September human-feedback revision packet,
`alternative-source-transfer/POST-TARGET-ACCOUNT.md` and
`ridge-endpoint-path/INTERPRETATION.md` under the DS methods directory.

Build one nested technical account, then give it to a fresh Sol agent. Have it
recover the supported claims, make a bounded agent/Jörn writing assignment, and
actually produce a coherent one-to-two-page passage. Separately assess source
meaning and usability. Record extra source reconstruction, unresolved decisions,
authoring/review cost and expected human work. Compare its benefit with the best
existing local account, not an artificially impoverished bare-repository baseline.
A small comparison can reveal failure; it will not estimate a general effect size.

- Wrong reconstruction: repair the account before multiplying topic authors.
- Correct reconstruction, but a plan hiding extensive rediscovery or missing
  evidence: repair/narrow the assignment and its mostly-agent allocation claim.
- Sound technical content but unusable prose: retain useful technical cleanup,
  stop expanding autonomous prose production, and escalate the exposed writing
  judgment to Jörn. Do not describe that as success of the complete writing route.
- Useful result: widen cautiously and use a second, different topic as a transfer
  check. One success is not a thesis-wide or seven-day forecast.

If Jörn is available, request one short contextual judgment on the actual frozen
passage and the reviewer's predicted obstacles. If he is unavailable, the human
usability question remains open; it must not silently become an AI-approved fact.
This is a targeted human contribution, not a request for him to design the workflow.

## 2. Can the reviewer distinguish the failures that matter?

**Move before its approval is used to justify scaling prose work.** Give the
proposed Sol reviewer a known failed historical DS sample with the verdict
withheld, together with an acceptable conservative control whose quality is
source-backed. Freeze the predictions before revealing the labels. Check for the
actual organizational/meaning failures, not generic nitpicks. Disclose historical
lineage or possible familiarity; passing is not independent acceptance validation.

The old reviewer-trial record already reports broad reviewers missing central DS
organization objections and narrower reviewers producing false alarms. If the
reviewer confidently accepts the known failure, or rejects everything, downgrade
its role to supported meaning checks/flagging and keep human acceptance explicit.
Do not spend the night repairing drafts against an evaluator that fails this
cheap discrimination check. Use the live passage in check 1 to test transfer.

## 3. Are the code/data migrations preserving the right contracts?

**Move before bulk caller migration, during the first small implementation
returns.** For geometry, capture duplicate/redundant/zero-row, rank-deficient and
unbounded cases, exact incidence and consumer-required ordering. Keep a
hand-checkable anchor and inspect which internals supposedly independent routes
share. Existing passing scalar anchors need not be rerun as a broad campaign.

For data, run the first unified builder through a real supported command on the
same small input bytes, including historical unknown metadata and malformed
inputs. Compare IDs, values, labels and provenance. This tests a complete change,
not just successful compilation.

Different input policies mean keep distinct adapters/shared primitives, not force
an equivalence. Schema change or fabricated historical metadata means stop that
migration, retain the thin loaders and isolate the required decision. Wrong
expectations are not frozen as a correctness oracle. These outcomes restrict
only dependent changes; proof consolidation and unrelated code work continue.

## 4. Can the delegation tree turn returns into integrated work?

**Move from the end-of-night merge to the first Sol-reviewed return.** Integrate
one geometry or data unit immediately, including a representative external
consumer. Observe review/integration queue growth, ownership conflicts, build
contention, repeated clarification and root intervention. If producers outrun
review/integration, shift capacity there before widening fan-out. If ownership
collides, serialize those files, not all work.

The actual cold-start launch is the first handover check: root must recover the
selected scope, owners, pending questions and next work. At an actual later
recovery, inspect processes and outputs before restarting writes. A separate
artificial process-restart exercise is not required before useful work. Missing
context at these checkpoints narrows unattended concurrency and triggers repair
of the concrete handover, rather than a new general coordination apparatus.

## What cannot move all the way forward

Whole-repository coherence, broad migration coverage, stable throughput and
whole-thesis readability still require later assembled checks. The early tests
are better at rejecting or narrowing a route than certifying all-night autonomy.
Keep final Astra review, supplied with these results and unresolved limits in
its single assembled reading packet. A material failure in the writing-value
chain reopens the overall value/spending decision; a local API or IO mismatch
usually changes only that branch.
